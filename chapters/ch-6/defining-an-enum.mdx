>Where structs give you a way of grouping together related fields and data, like a `Rectangle` with its `width` and `height`, <u>enums (enumerations) give you a way of saying a value is one of a possible set of values</u>. For example, we may want to say that `Rectangle` is one of a set of possible shapes that also includes `Circle` and `Triangle`. To do this, Rust allows us to encode these possibilities as an enum.

>Say we need to work with IP addresses. Currently, two major standards are used for IP addresses: version four and version six. Because these are the only possibilities for an IP address that our program will come across, we can enumerate all possible variants, which is where enumeration gets its name.

>Any IP address can be either a version four or a version six address, but not both at the same time. Both version four and version six addresses are still fundamentally IP addresses, so they should be treated as the same type when the code is handling situations that apply to any kind of IP address.

>We can express this concept in code by defining an `IpAddrKind` enumeration and listing the possible kinds an IP address can be: `V4` and `V6`.

```rust Code 6.1.1
enum IpAddrKind {
    V4,
    V6,
}
```

><u>`IpAddrKind` is now a custom data type</u> that we can use elsewhere in our code.

## Enum Values

>We can create <u>instances</u> of each of the two <u>variants</u> of `IpAddrKind` like this:

>- `let four = IpAddrKind::V4;`
>- `let six = IpAddrKind::V6;`

>Note that the variants of the enum are <u>namespaced</u> under its identifier, and we use a double colon to separate the two. This is useful because now both values `IpAddrKind::V4` and `IpAddrKind::V6` are of the same type: `IpAddrKind`. We can then, for instance, define a function that takes any `IpAddrKind`:

>`fn route(ip_kind: IpAddrKind) {}`

>And we can call this function with either variant:

>- `route(IpAddrKind::V4);`
>- `route(IpAddrKind::V6);`

>Thinking more about our IP address type, at the moment we don’t have a way to store the actual IP address data; we only know what kind it is. Given that you just learned about structs in Ch. 5, you might be tempted to tackle this problem with structs as shown in Code 6.1.2.

```rust Code 6.1.2
enum IpAddrKind {
    V4,
    V6,
}

struct IpAddr {
    kind: IpAddrKind,
    address: String,
}

fn main() {
    let home = IpAddr {
        kind: IpAddrKind::V4,
        address: String::from("127.0.0.1"),
    };

    let loopback = IpAddr {
        kind: IpAddrKind::V6,
        address: String::from("::1"),
    };
}
```

>We’ve used a struct to bundle the `kind` and `address` values together, so now the variant is associated with the value. However, <u>representing the same concept using just an enum is more concise</u>: Rather than an enum inside a struct, <u>we can put data directly into each enum variant</u>. This new definition of the `IpAddr` enum says that both `V4` and `V6` variants will have associated `String` values:

```rust Code 6.1.3
enum IpAddr {
    V4(String),
    V6(String),
}

fn main {
    let home = IpAddr::V4(String::from("127.0.0.1"));

    let loopback = IpAddr::V6(String::from("::1"));
}
```

>Here, it’s also easier to see another detail of how enums work: <u>The name of each enum variant that we define also becomes a function that constructs an instance of the enum</u>. That is, <u>`IpAddr::V4()` is a function call that takes a `String` argument and returns an instance of the `IpAddr` type</u>.

><p><u>We automatically get this constructor function defined as a result of defining the enum.</u></p>

>There’s another advantage to using an enum rather than a struct: <u>Each variant can have different types and amounts of associated data</u>. Version four IP addresses will always have four numeric components that will have values between 0 and 255. <u>If we wanted to store `V4` addresses as four `u8` values but still express `V6` addresses as one `String` value, we wouldn’t be able to with a struct. Enums handle this case with ease:</u>

```rust Code 6.1.4
enum IpAddr {
    V4(u8, u8, u8, u8),
    V6(String),
}

fn main() {
    let home = IpAddr::V4(127, 0, 0, 1);

    let loopback = IpAddr::V6(String::from("::1"));
}
```

>Let’s look at <u>how the standard library defines `IpAddr`</u>. It has the exact enum and variants that we’ve defined and used, but it embeds the address data inside the variants in the form of two different structs, which are defined differently for each variant:

```rust Code 6.1.5
struct Ipv4Addr {
    // --snip--
}

struct Ipv6Addr {
    // --snip--
}

enum IpAddr {
    V4(Ipv4Addr),
    V6(Ipv6Addr),
}
```

>This code illustrates that <u>you can put any kind of data inside an enum variant</u>: strings, numeric types, or structs, for example. <u>You can even include another enum!</u> Also, standard library types are often not much more complicated than what you might come up with.

It is important to pause here for a moment to fully grasp what has just been shown. First of all—and the official book does not explicitly highlight this—<u>`enum IpAddr { V4(Ipv4Addr), V6(Ipv6Addr), }` is an enum whose variants behave exactly like tuple-structs, each containing a different standard struct</u>!

<u>Tuple-structs are essentially labeled tuples designed to improve readability and clarity, and they are idiomatically unpacked using pattern matching constructs</u>, which the official book introduces in the very next section (this is no coincidence, of course; indeed, enums are highly idiomatic when used together with pattern matching constructs as well).

<u>The fact that the standard library uses this pattern clearly demonstrates the power of these data structures in Rust. Their readability, clear organization, and concise syntax—combined with how perfectly they integrate with pattern matching—make enums and tuple-structs constructs of key importance in Rust.</u> This is exactly what the standard library's implementation of `IpAddr` represents: to all effects, it embodies an `enum(tuple-struct(struct))` architecture.

It is also important to note, however, that while this structural composition is highly effective for improving readability and unlocking the full potential of pattern matching, <u>it can sometimes introduce redundancy</u>. This is clearly visible in the `IpAddr` example: <u>the types inside the tuple-like variants labeled `V4`/`V6` are `Ipv4Addr`/`Ipv6Addr`, making the `V4`/`V6` labels feel somewhat repetitive</u>.

We accept this trade-off because of the structural benefits mentioned earlier, and because of how the code is actually used in practice. Outside of the `IpAddr` enum definition itself, you rarely write out the explicit `Ipv4Addr`/`Ipv6Addr` type names. <u>When instantiating the enum in real code, the inner data will almost certainly be passed as a variable. At that point—at the call site—the `V4`/`V6` labels improve readability, immediately clarifying what the variables represent.</u>

>Note that even though the standard library contains a definition for `IpAddr`, we can still create and use our own definition without conflict because <u>we haven’t brought the standard library’s definition into our scope</u>. We’ll talk more about bringing types into scope in Ch. 7.

>Let’s look at another example of an enum in Code 6.1.6: This one has a wide variety of types embedded in its variants.

```rust Code 6.1.6
enum Message {
    Quit,
    Move { x: i32, y: i32 },
    Write(String),
    ChangeColor(i32, i32, i32),
}
```

>This enum has four variants with different types:

>- `Quit`: Has no data associated with it at all (it's an unit-like struct variant).
>- `Move`: Has named fields, like a struct does (it's a struct variant).
>- `Write`: Includes a single `String` (it's a tuple-struct variant).
>- `ChangeColor`: Includes three `i32` values (it's a tuple-struct variant).

><u>Defining an enum with variants such as the ones in Code 6.1.6 is similar to defining different kinds of struct definitions, except the enum doesn’t use the `struct` keyword and all the variants are grouped together under the `Message` type.</u> The following structs could hold the same data that the preceding enum variants hold:

```rust Code 6.1.7
struct QuitMessage; // unit-like struct
struct MoveMessage {
    x: i32,
    y: i32,
}
struct WriteMessage(String); // tuple-struct
struct ChangeColorMessage(i32, i32, i32); // tuple-struct
```

>But <u>if we used the different structs, each of which has its own type, we couldn’t as easily define a function to take any of these kinds of messages as we could with the `Message` enum</u> defined in Code 6.1.6, which is a single type.

>There is one more similarity between enums and structs: <u>Just as we’re able to define methods on structs using `impl`, we’re also able to define methods on enums</u>. Here’s a method named `call` that we could define on our `Message` enum:

```rust Code 6.1.8
// --snip--

impl Message {
    fn call(&self) {
        // method body would be defined here
    }
}

fn main() {
    let m = Message::Write(String::from("hello")); /* Remember Message is an enum, you can
                                                      only use 1 variant at a time. */
    m.call();
}
```

>The body of the method would use `self` to get the value that we called the method on. In this example, we’ve created a variable `m` that has the value `Message::Write(String::from("hello"))`, and that is what `self` will be in the body of the `call` method when `m.call()` runs.

Note also that <u>you can define an `impl` block for a tuple-struct</u> as well.

## Architectural Layers in Rust

At this point, Rust's composability can start to feel quite overwhelming. For this reason, a general schema is outlined below.

```math
\underbrace{\text{tuple-struct ?}\hspace{0.3cm}\underbrace{\text{struct ?}\hspace{0.3cm}\text{data (primitive types / collections) ?}}_\text{enum ?}}_\text{enum ?}
```

This schema does not mandate the existence of every structure shown (which is why each element is marked with a `?`). In practice, <u>they can be organized in many different ways</u>; however, this hierarchy provides a solid general overview of how proper encapsulation is typically modeled.

There is one notable scenario that this top-down schema does not capture: <u>a struct that contains an enum (which, in turn, might contain other structs)</u>. Because this creates a potential loop in the architectural hierarchy, it cannot be easily depicted in a simple linear diagram.

For example, consider a `User` struct that tracks an account status:

```rust Code 6.1.9
struct User {
    username: String,
    status: UserStatus, // struct -> enum
}

enum UserStatus {
    Active,
    Banned,
    PendingApproval(String), // enum -> tuple-struct -> String struct
}
```

Another architectural approach that bypasses the schema above is the **Newtype pattern**. <u>This pattern is used to enforce type safety by wrapping a raw primitive type directly inside a single-element tuple struct. By doing so, the compiler prevents you from accidentally mixing up identical primitive types.</u>

For example, even if both represent a `u32` under the hood, the compiler will not let you accidentally pass miles to a function expecting kilometers:

```rust Code 6.1.10
// Wrapping raw data directly into tuple-structs.
struct Kilometers(u32);
struct Miles(u32);

fn process_distance(dist: Kilometers) {
    // --snip--
}

fn main() {
    let distance_km = Kilometers(50);
    let distance_mi = Miles(30);
    
    process_distance(distance_km); // Works perfectly.
    // process_distance(distance_mi); // ERROR: Expected Kilometers, found Miles.
}
```

>Let’s now look at another enum in the standard library that is very common and useful: `Option`.

## The `Option` Enum

We already saw the `Option<T>` enum in action in section 4.3. Here, however, we will follow the official book and analyze it in greater detail due to its fundamental importance.

><p><u>The `Option` type encodes the very common scenario in which a value could be something, or it could be nothing.</u></p>

>For example, if you request the first item in a non-empty list, you would get a value. If you request the first item in an empty list, you would get nothing. <u>Expressing this concept in terms of the type system means the compiler can check whether you’ve handled all the cases you should be handling; this functionality can prevent bugs that are extremely common in other programming languages.</u>

><u>Rust doesn’t have the null feature that many other languages have.</u> Null is a value that means there is no value there. In languages with null, variables can always be in one of two states: null or not-null.

>In his 2009 presentation “Null References: The Billion Dollar Mistake”, Tony Hoare, the inventor of null, had this to say:

<Info>
>I call it my billion-dollar mistake. At that time, I was designing the first comprehensive type system for references in an object-oriented language. My goal was to ensure that all use of references should be absolutely safe, with checking performed automatically by the compiler. But I couldn’t resist the temptation to put in a null reference, simply because it was so easy to implement. This has led to innumerable errors, vulnerabilities, and system crashes, which have probably caused a billion dollars of pain and damage in the last forty years.
</Info>

><p><u>The problem with null values is that if you try to use a null value as a not-null value, you’ll get an error of some kind. Because this null or not-null property is pervasive, it’s extremely easy to make this kind of error.</u></p>

>However, <u>the concept that null is trying to express is still a useful one: A null is a value that is currently invalid or absent for some reason</u>.

><u>The problem isn’t really with the concept but with the particular implementation.</u> As such, <u>Rust does not have nulls, but it does have an enum that can encode the concept of a value being present or absent. This enum is `Option<T>`</u>, and it is defined by the standard library as follows:

```rust Code 6.1.11
enum Option<T> {
    None,
    Some(T),
}
```

><u>The `Option<T>` enum is so useful that it’s even included in the prelude; you don’t need to bring it into scope explicitly. Its variants are also included in the prelude: You can use `Some` and `None` directly without the `Option::` prefix.</u> The `Option<T>` enum is still just a regular enum, and `Some(T)` and `None` are still variants of type `Option<T>`.

>The `<T>` syntax is a feature of Rust we haven’t talked about yet. It’s a **generic type** parameter, and we’ll cover generics in more detail in Ch. 10. For now, all you need to know is that <u>`<T>` means that the `Some` variant of the `Option` enum can hold one piece of data of any type, and that each concrete type that gets used in place of `T` makes the overall `Option<T>` type a different type</u>. Here are some examples of using `Option` values to hold number types and char types:

```rust Code 6.1.12
fn main() {
    let some_number = Some(5);
    let some_char = Some('e');

    let absent_number: Option<i32> = None;
}
```

><p><u>The type of `some_number` is `Option<i32>`. The type of `some_char` is `Option<char>`, which is a different type. Rust can infer these types because we’ve specified a value inside the `Some` variant. For `absent_number`, Rust requires us to annotate the overall `Option` type: The compiler can’t infer the type that the corresponding `Some` variant will hold by looking only at a `None` value.</u></p>

>When we have a `Some` value, we know that a value is present, and the value is held within the `Some`. <u>When we have a `None` value, in some sense it means the same thing as null: We don’t have a valid value. So, why is having `Option<T>` any better than having null?</u>

><u>In short, because `Option<T>` and `T` (where `T` can be any type) are different types, the compiler won’t let us use an `Option<T>` value as if it were definitely a valid value.</u> For example, this code won’t compile, because it’s trying to add an `i8` to an `Option<i8>`:

<CodeGroup>
```rust Code 6.1.13
fn main() {
    let x: i8 = 5;
    let y: Option<i8> = Some(5);

    let sum = x + y;
}
```
```text C-Output 6.1.13
error[E0277]: cannot add `Option<i8>` to `i8`
 --> src/main.rs:5:17
  |
5 |     let sum = x + y;
  |                 ^ no implementation for `i8 + Option<i8>`
  |
  = help: the trait `Add<Option<i8>>` is not implemented for `i8`
  = help: the following other types implement trait `Add<Rhs>`:
            `&i8` implements `Add<i8>`
            `&i8` implements `Add`
            `i8` implements `Add<&i8>`
            `i8` implements `Add`
            
For more information about this error, try `rustc --explain E0277`.
error: could not compile `enums` (bin "enums") due to 1 previous error
```
</CodeGroup>

>C-Output 6.1.13 means that <u>Rust doesn’t understand how to add an `i8` and an `Option<i8>`, because they’re different types</u>. <u>When we have a value of a type like `i8` in Rust, we can proceed confidently without having to check for null before using that value. Only when we have an `Option<i8>` (or whatever type of value we’re working with) do we have to worry about possibly not having a value, and the compiler will make sure we handle that case before using the value.</u>

>In other words, <u>you have to convert an `Option<T>` to a `T` before you can perform operations with it</u>. Generally, <u>this helps catch one of the most common issues with null: assuming that something isn’t null when it actually is</u>.

>Eliminating the risk of incorrectly assuming a not-null value helps you be more confident in your code. <u>In order to have a value that can possibly be null, you must explicitly opt in by making the type of that value `Option<T>`. Then, when you use that value, you are required to explicitly handle the case when the value is null. Everywhere that a value has a type that isn’t an `Option<T>`, you can safely assume that the value isn’t null.</u> This was a deliberate design decision for Rust to limit null’s pervasiveness and increase the safety of Rust code.

>So how do you get the `T` value out of a `Some` variant when you have a value of type `Option<T>` so that you can use that value? The `Option<T>` enum has a large number of methods that are useful in a variety of situations. Becoming familiar with the methods on `Option<T>` will be extremely useful in your journey with Rust.

>In general, <u>in order to use an `Option<T>` value, you want to have code that will handle each variant</u>. <u>You want some code that will run only when you have a `Some(T)` value, and this code is allowed to use the inner `T`. You want some other code to run only if you have a `None` value, and that code doesn’t have a `T` value available. The `match` expression is a control flow construct that does just this when used with enums: It will run different code depending on which variant of the enum it has, and that code can use the data inside the matching value.</u>
