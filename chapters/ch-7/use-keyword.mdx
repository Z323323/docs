>Having to write out the paths to call functions can feel inconvenient and repetitive. Fortunately, there’s a way to simplify this process: <u>We can create a shortcut to a path with the `use` keyword once and then use the shorter name everywhere else in the scope</u>.

In Code 7.4.1, we use the `use` keyword to bring `crate::front_of_house::hosting` (defined in _~/rust_projects/restaurant/src/front_of_house/hosting/mod.rs_) into the global scope of _lib.rs_. This creates a shortcut so that, when writing the `eat_at_restaurant` function, we only need to call `hosting::add_to_waitlist` instead of writing out the full path.

```rust Code 7.4.1
mod front_of_house;
mod back_of_house;

use crate::front_of_house::hosting;

pub fn eat_at_restaurant() {
    // Absolute path
    crate::front_of_house::hosting::add_to_waitlist();

    // Relative path
    front_of_house::hosting::add_to_waitlist();
    
    // Absolute path shortcut
    hosting::add_to_waitlist();
}

fn deliver_order() {}
```

Remember this is possible because `front_of_house` is a sibling of `eat_at_restaurant` (it's not defined with the `pub` keyword), while `hosting` and `add_to_waitlist` are both defined as `pub`.

>Note that <u>`use` only creates the shortcut for the particular scope in which the `use` occurs</u>.

## Creating Idiomatic `use` Paths

>In Code 7.4.1, you might have wondered why we specified `use crate::front_of_house::hosting` and then called `hosting::add_to_waitlist` in `eat_at_restaurant`, rather than specifying the `use` path all the way out to the `add_to_waitlist` function to achieve the same result, as in Code 7.4.2.

```rust Code 7.4.2
mod front_of_house;
mod back_of_house;

use crate::front_of_house::hosting::add_to_waitlist;

pub fn eat_at_restaurant() {
    // Absolute path
    crate::front_of_house::hosting::add_to_waitlist();

    // Relative path
    front_of_house::hosting::add_to_waitlist();
    
    // Absolute path shortcut
    add_to_waitlist();
}

fn deliver_order() {}
```

>Although both Code 7.4.1 and Code 7.4.2 accomplish the same task, <u>Code 7.4.1 is the idiomatic way to bring a function into scope with `use`</u>. <u>Bringing the function’s parent module into scope with `use` means we have to specify the parent module when calling the function. Specifying the parent module when calling the function makes it clear that the function isn’t locally defined while still minimizing repetition of the full path.</u> Code 7.4.2 is unclear as to where `add_to_waitlist` is defined.

>On the other hand, <u>when bringing in structs, enums, and other items with `use`, it’s idiomatic to specify the full path</u>. Code 7.4.3 shows the idiomatic way to bring the standard library’s `HashMap` struct into the scope of a binary crate.

```rust Code 7.4.3
use std::collections::HashMap;

fn main() {
    let mut map = HashMap::new();
    map.insert(1, 2);
}
```

><u>The exception to this idiom is if we’re bringing two items with the same name into scope</u> with `use` statements, because Rust doesn’t allow that. Code 7.4.4 shows how to bring two `Result` types into scope that have the same name but different parent modules, and how to refer to them.

```rust Code 7.4.4
use std::fmt;
use std::io;

fn function1() -> fmt::Result {
    // --snip--
}

fn function2() -> io::Result<()> {
    // --snip--
}
```

>As you can see, using the parent modules distinguishes the two `Result` types. If instead we specified `use std::fmt::Result` and `use std::io::Result`, we’d have two `Result` types in the same scope, and Rust wouldn’t know which one we meant when we used `Result`.

## Providing New Names with the `as` Keyword

>There’s another solution to the problem of bringing two types of the same name into the same scope with `use`: After the path, we can specify as and a new local name, or alias, for the type. Code 7.4.5 shows another way to write the code in Code 7.4.4 by renaming one of the two `Result` types using `as`.

```rust Code 7.4.5
use std::fmt::Result;
use std::io::Result as IoResult;

fn function1() -> Result {
    // --snip--
}

fn function2() -> IoResult<()> {
    // --snip--
}
```

>In the second `use` statement, we chose the new name `IoResult` for the `std::io::Result` type, which won’t conflict with the `Result` from `std::fmt` that we’ve also brought into scope. Code 7.4.4 and Code 7.4.5 are considered idiomatic, so the choice is up to you!

## Re-exporting Names with `pub use`

><u>When we bring a name into scope with the `use` keyword, the name is private to the scope into which we imported it. To enable code outside that scope to refer to that name as if it had been defined in that scope, we can combine `pub` and `use`.</u> This technique is called **re-exporting** because we’re bringing an item into scope but also making that item available for others to bring into their scope.

>Code 7.4.6 shows Code 7.4.1 with `use` in the root module changed to `pub use`.

```rust Code 7.4.6
// --snip--

pub use crate::front_of_house::hosting;

// --snip--
```

>Before this change, external code would have to call the `add_to_waitlist` function by using the path `restaurant::front_of_house::hosting::add_to_waitlist()`, which also would have required the `front_of_house` module to be marked as `pub`. Now that this `pub use` has re-exported the `hosting` module from the root module, <u>external code can use the path `restaurant::hosting::add_to_waitlist()`</u> instead.

<Warning>
You must be particularly careful when using `pub use`. Because it acts as a module re-export, <u>it can completely bypass the carefully crafted security of your architecture</u>!

## Using External Packages

>In Ch. 2, we programmed a guessing game project that used an external package called `rand` to get random numbers. To use `rand` in our project, we added `rand = "0.8.5"` to _Cargo.toml_.

>Adding `rand` as a dependency in _Cargo.toml_ tells Cargo to download the `rand` package and any dependencies from [[crates.io](https://crates.io)] and make `rand` available to our project.

>Then, to bring `rand` definitions into the scope of our package, we added the `use rand::Rng` line starting with the name of the crate, `rand`, and listed the items we wanted to bring into scope.

>Note that the standard `std` library is also a crate that’s external to our package. Because the standard library is shipped with the Rust language, we don’t need to change _Cargo.toml_ to include `std`. But we do need to refer to it with `use` to bring items from there into our package’s scope. For example, with `HashMap` we would use the line `use std::collections::HashMap`.

## Using Nested Paths to Clean Up use Lists

>If we’re using multiple items defined in the same crate or same module, listing each item on its own line can take up a lot of vertical space in our files. For example, the `use std::cmp::Ordering` and `use std::io` statements we had in the guessing game in Ch. 2 bring items from `std` into scope.

>Instead, we can use nested paths to bring the same items into scope in one line.

For example, by writing `use std::{cmp::Ordering, io}` we bring both `std::cmp::Ordering` and `std::io` in scope, in a single line.

>In bigger programs, bringing many items into scope from the same crate or module using nested paths can reduce the number of separate `use` statements needed by a lot!

>We can use a nested path at any level in a path, which is useful when combining two `use` statements that share a subpath. For example, `use std::io::{self, Write}` brings `std::io` and `std::io::Write` into scope.

## Importing Items with the Glob Operator

>If we want to bring all public items defined in a path into scope, we can specify that path followed by the `*` glob operator: `use std::collections::*`.

>This `use` statement brings all public items defined in `std::collections` into the current scope. Be careful when using the glob operator! Glob can make it harder to tell what names are in scope and where a name used in your program was defined.
